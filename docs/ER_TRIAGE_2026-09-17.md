### `1fe2707e` -- Lynn: "sourced parts approved" -> notify the parts manager

*sourced parts approved* so the **parts manager** is notified to place the order.

Confirmed absent at HEAD `ac11d35`:

- `repair_orders_parts_status_check` allows only
  `requested | sourcing | ordered | received | estimate`
  (`supabase/migrations/parts_status_phase2_drop_outstanding.sql` L25).
  There is no approved/authorized value.
- `openPartsStatusModal` (`js/parts.js` L796-814) renders exactly those five
  buttons plus Clear. The only requester-facing control in that modal is the
  manual "Notify Requester - Parts Ordered" button (L816), which is the wrong
  direction (parts dept -> requester, after the fact).
- `setPartsStatus` (L825-881) writes `parts_status`, an RO note and an audit row.
  No approval gate, no notification, no record of who approved.

Build shape (M, one session):

1. Migration: new `parts_status` value (or a separate `parts_approved_at` /
   `parts_approved_by` pair, which avoids widening the status enum). If a new
   status value is chosen, remember the S172 lesson -- check whether the
   `cashiered` twin carries the column (it does **not** for `parts_status`,
   verified in the Phase 2 migration header, so only one CHECK needs widening).
2. An "Approve sourced parts" action visible when `parts_status='sourcing'`,
   gated to the requester (`ro.requestedByEmail`, captured by
   `submitPartsRequest` at `js/parts.js` L683) plus managers/admins.
3. Parts-manager notify: reuse the `_notifyApprovalStatus` recipient+queue
   pattern (`js/ro-crud.js` L481-560) but resolve recipients as
   `staff.role='parts_manager'` -- exact precedent in
   `supabase/functions/send-parts-report/index.ts` L165-169. Needs a one-line
   `scheduled_notifications.source` CHECK widening (template:
   `approval_notify_source_s175.sql`).

### `5c3b14eb` -- Brandon: click the card dollar amount and edit it directly

Confirmed absent at HEAD `ac11d35`: `js/render.js` L442-446 renders

```
<div class="dollar-value">$${ro.dollarValue.toLocaleString()}</div>
```

-- a plain `div`, no `data-action`, so the board click delegation
(`index.html` L4108-4157) never sees it. Today the only editor is the Edit RO
modal input `editDollarValue` (`js/ro-crud.js` L1813).

The pattern to reuse already exists: `data-action="edit-field"` +
`class="editable-field"` dispatches to `editField` (`js/ro-crud.js` L1679), and
the audit writer is already numeric-aware for `dollarValue` (`index.html` L353,
field map L2711). That makes the mechanics small.

**Two cautions that should be settled before building:**

1. **`dollar_value` is a derived roll-up.** `computeAndSaveWORollup`
   (`js/work-orders.js` L750-761) sums `service_work_orders.dollar_value` and
   overwrites `repair_orders.dollar_value` on every WO save. A hand-typed card
   value is therefore silently clobbered the next time anyone saves a work
   order. (Edit RO already has this conflict -- L604/L684 write the column
   directly -- so the inline editor exposes an existing problem rather than
   creating one.) Decide: edit the roll-up source instead, or accept and label
   the override. Worth pairing with Jason's `2f752d40` (WO dollar autofill),
   which touches the same money path.
2. **The target is hidden by default.** `tileVisibility.dollarValue` is `false`
   in the **Condensed** preset (`index.html` L1636) and `true` in Regular
   (L1657). This is exactly Brandon's other open ER `5dc697e2` ("I used to be
   able to see the repair order totals on the front page"). Ship `5dc697e2`
   with or before this one, otherwise for Condensed users there is nothing to
   click.
3. Permission: WO pricing is already gated -- `dollarLocked`
   (`js/work-orders.js` L324) makes the field read-only for
   insurance-WO-writer-only roles once a value is set. Mirror that gate on the
   card editor rather than letting every role retype totals.

### `c15727a3` -- Lynn: notify the requester when parts are marked received

Confirmed absent at HEAD `ac11d35`:

- `setPartsStatus` (`js/parts.js` L825-881) performs the DB update, the RO note
  and the audit row, then `renderBoard()`. There is no notification on any
  transition, `received` included.
- The only requester-facing emails in the module are the **manual**
  "Notify Requester - Parts Ordered" button (L816 ->
  `_doNotifyPartsRequester`, `index.html` L5923) and `notifyPartsEtaUpdate`
  (L901). `supabase/functions/send-quote-email/index.ts` implements
  `parts_ordered` (L227) and `parts_eta_update` (L323) only -- there is no
  `parts_received` template.
- There used to be a received notification: the Slack `part_received` call site
  was deleted in v1.445 (S92), and the comment marking its removal is still at
  `js/parts.js` L459. So this is a capability regression from the Slack
  teardown, not a never-built feature.

Build shape (S, under 2h):

- Hook the notify **inside `setPartsStatus`** on the `-> received` edge. That is
  load-bearing: `received` is reached by three paths -- the status-modal button
  (L806), the `savePartForm` auto-flip (L404) and the `markPartReceived`
  auto-flip (L466). The latter two both delegate to `setPartsStatus`, so one
  hook covers all three; hooking the button alone would miss the common case.
- Add a `parts_received` branch to `send-quote-email` mirroring `parts_ordered`.
- Guard on `ro.requestedByEmail`, which is null unless the parts were requested
  through the Request Parts flow (`js/parts.js` L683). For older ROs, fall back
  to the silo manager rather than sending nothing silently.
- Natural batch-mate for Brandon's two open received-date ERs, `2af47890` and
  `1e434aff`.
