## The one ER classified this run

`a195e4ab` - Brandon Dillon, 2026-08-20, General UI/UX, status `unreviewed`.

> "In the Repair Orders, there should be a section to add information about
> checks that way we can better track that, and add any additional ones we
> receive"

Read as payment checks received against an RO (customer and insurance), with the
ability to append each additional check as it arrives. Mapped by reading the
code, not assumed:

- No check tracking exists anywhere. `check_number`, `checkNumber`,
  `check_amount`, `checksReceived` and `payments` return **zero hits** across
  `js/*.js`, `index.html` and `supabase/migrations/*.sql`.
- The only payment capture in the product is the **Customer Pay Details** block
  (`index.html` L7203-7246 New RO, L7782-7804 Edit RO): Customer Pay Amount,
  Balance Due, Pay Status, Payment Method, Customer Invoice Number, Date Paid,
  Pay Description.
- That block is **hybrid-RO-only** - `setROType` adds the `visible` class to
  `customerPaySection` / `editCustomerPaySection` only in the `hybrid` branch
  (`index.html` L2263-2267). A Standard, Insurance, Warranty or Shop RO has no
  payment fields at all.
- Payment Method offers `Check` (L7229 New, L7797 Edit) but there is **no field
  for the check number, the payer, or a per-check amount**, and the block holds
  exactly **one** amount and **one** `datePaid` - it cannot record a second
  check.
- The values are collected into a flat object (`collectInsuranceFields`
  L2414-2423) and written into the `repair_orders.insurance_data` JSONB blob
  (`writeInsuranceData` call sites L6562 create / L6718 edit; read back in
  `js/ro-crud.js` L1219, L1248-1255). There is no row-per-payment structure.
- Nothing from that block is rendered on the RO card: `customerPay`,
  `Balance Due` and `paymentMethod` return **zero hits** in `js/render.js`, so
  even the single payment already capturable is invisible outside the Edit modal.

**Bucket: `needed`. LOE: M. Theme: RO Fields & Status.** A repeatable per-RO
`ro_payments` / `ro_checks` child table (check number, payer/source, amount,
date received, deposited flag, note), an add-and-list UI in the RO card or Edit
modal, a card readout, and a `cashiered_child_archives` mirror so the history
survives cash-out - that last part is the direct lesson of `09084bc5` / S171.
Filed `needed` rather than `done` deliberately: the Check option in the Payment
Method dropdown is the closest existing thing, and it satisfies neither half of
the ask (no check detail, no additional checks).

Underspecified in one respect worth confirming with Brandon before building:
whether this covers **insurance** checks (initial + supplement drafts) as well as
customer checks. The answer decides whether the section hangs off the
hybrid-only Customer Pay block or becomes a payments section on every RO type.
The verdict assumes the latter.
